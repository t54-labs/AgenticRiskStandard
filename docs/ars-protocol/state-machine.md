# State Machine

ARS uses a deterministic state machine that derives job state by replaying the event log. The state machine enforces transition rules, role permissions, and ordering constraints.

## Phases

Every job progresses through five phases:

```
REQUEST → NEGOTIATION → TRANSACTION → EVALUATION → CLOSED
```

**REQUEST** is the initial phase when a job is created but no agreement exists yet.

**NEGOTIATION** begins when the first agreement draft is proposed. Parties can submit counter-proposals. Both the requestor and business agent must sign to proceed.

**TRANSACTION** begins when both parties have signed the agreement. The fee track and (optionally) principal track are now active. Fee can be locked, deliverables submitted, and underwriting requested.

**EVALUATION** begins when a deliverable has been submitted and the evaluator has issued a verdict.

**CLOSED** is the terminal phase after the fee has been settled (released or refunded).

## State Derivation

State is computed by `derive_job_state(events)`, which initializes an accumulator and replays each event in order. The accumulator tracks:

- Agreement and agreement hash
- Signatures from each party
- Fee lock reference
- Deliverable reference
- Evaluation verdict
- Settlement reference and action
- UW decision, premium, collateral status
- Override decisions
- Release approvals
- Transfer reference and execution evidence

After replaying all events, the function derives the phase, fee track state, and principal track state from the accumulated data.

## Transition Validation

Before any event is appended, `validate_transition(state, envelope)` checks:

1. **Phase check**: Is this event type allowed in the current phase? For example, `AGREEMENT_SIGNED` is only allowed during `NEGOTIATION`.

2. **State check**: Is the current track state correct for this event? For example, `FEE_ESCROW_LOCKED` requires `FEE_AWAIT_LOCK`.

3. **Role check**: Is the actor authorized for this action? For example, only the requestor can lock fees, only the evaluator can evaluate.

4. **Agreement hash check**: Does the envelope's agreement hash match the stored hash? (All post-creation events must reference the correct agreement.)

Invalid transitions return HTTP 409 (Conflict). Unauthorized actors return HTTP 403 (Forbidden). Bad requests return HTTP 400.

## Event Types

The protocol defines 18 event types across both tracks:

**Fee track events:**
`JOB_CREATED`, `PROPOSAL_SUBMITTED`, `AGREEMENT_SIGNED`, `FEE_ESCROW_LOCKED`, `DELIVERABLE_SUBMITTED`, `OUTCOME_EVALUATED`, `FEE_SETTLED`

**Principal track events:**
`UW_REQUESTED`, `UW_DECIDED`, `PREMIUM_PAID`, `PREMIUM_REFUSED`, `COLLATERAL_LOCKED`, `COLLATERAL_REFUSED`, `OVERRIDE_DECIDED`, `RELEASE_APPROVED`, `PRINCIPAL_RELEASED`, `EXECUTION_EVIDENCE_SUBMITTED`

## Shared Router

14 of the server endpoints (proposals, signatures, deliverable, evaluate, all UW operations, and GET endpoints) share identical logic between the abstract and concrete implementations. These are generated by a parameterized router factory (`create_shared_router`) that accepts pluggable state derivation and validation functions. This means the transition rules and role checks are defined once and reused by all implementations.

The 5 remaining endpoints (job creation, fee lock, fee settle, collateral lock, principal release) are defined separately in each server because they interact with the settlement layer, which has different implementations (mock vaults vs. on-chain contracts).
